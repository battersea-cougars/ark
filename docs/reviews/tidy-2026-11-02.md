## CI

The workflows were cleaned up earlier (#148, 8016220 and #217): one setup action (Node from `.nvmrc`, `node_modules`
cached on the lockfile), one secrets action, PR checks by the `merge:check` tiers, and the one-off "Retire old Worker
secrets" steps are gone now both environments have deployed.

**Deploy only what changed** (`deploy.yml`'s `changes` job) was checked against the last twelve merges into main: a
team-app-only change deploys the team app alone, a website change the website alone, a docs or templates change
nothing, and a change to shared code, the lockfile or the workflow everything. One hole fixed:
`scripts/lib/kumite-sql.mjs`, which the website's build reads through the club snapshot, wasn't in the website's
paths, so a change there alone wouldn't have rebuilt the site.

Left as they are, for a later look:

- The `database` job's paths include `deploy.yml`, so any change to the workflow backs up and rebuilds (later,
  migrates) the database. Safe (it backs up first, and a migrate with nothing new does nothing) but slow; the
  workflow's own changes could leave the database alone once that's agreed.
- `db/` is in the shared paths, so a seed change also deploys the Studio, which doesn't read D1.
- The web and team jobs repeat the "Source maps" step with a different project and path; a composite action would
  hold it once, but it's two short copies.
- `changes` checks out the whole history (`fetch-depth: 0`) to diff against the push's `before`; the repo is 18 MB
  packed, so a blob-less clone would save little.

**The slowest jobs** (recent successful runs): journeys about 9 minutes (nightly and on `release`, never blocking),
the store app's iOS build about 8 minutes (a macOS runner, only when the shell changes), the PR check about 5 minutes
(lint, knip, tests, both apps' checks and builds), the deploy's `database` job about 2 minutes (backup, then the
rebuild), and the app deploys under a minute each. The repo is public, so the runners cost nothing; the minutes only
matter for waiting.
